22 · Record Button

§18's capture step, collapsed into one control: the primary CTA, at all three targets. Two states — ready ⇄ recording — and every switch resets the clock, so there is no third “recorded” state to explain. Use §18 instead when the user has to replay or delete the note before moving on; that needs a playback state and a second button.

It is §04 CTA Button with two extra parts — the meter and the readout — so hover, active, focus, disabled and the 44 / 56 / 64 target ladder are inherited rather than re-derived. The size raises the target and the glyph step, never the type step.

The state is not carried by hue. The button stays primary while live: §18's red-while-live belongs to a bordered surface, and on the screen's main action the same move paints a working control as a failure. Three cues change instead — the glyph (mic → stop), the label, and the meter, which exists only while recording — so the state survives greyscale and forced colours (1.4.1) with no colour swap at all.

The meter is decorative; the counter is not. Bars are aria-hidden and take currentColor, so they follow the button's ink in every variant and in the disabled state with no rule of their own; what a screen-reader user gets is the readout — seconds in, seconds left, in a role="status" region. The bar count is fixed, because a meter that changes bar count with the signal reads as a layout bug rather than as a level. Under reduced motion the meter flattens to a still row: Layer 1's 1 ms would strobe live data rather than shorten it, which is the decision §18 took for its pulse.

Two decisions worth arguing with. The readout shows both figures where §21 shows only the countdown — a speaker needs to know they are being recorded and how much room is left, and a 60-second ceiling makes “48 left” actionable in a way a track's remaining time is not. And the meter is the elastic part: the label is a label step and must not wrap at a 44px target, and the readout is the only thing a screen-reader user gets — so the bars take the whole deficit and clip from the leading edge, which is the oldest end of the signal. The ready state's width is held so the button does not jump wider the moment it goes live, and the comfort and guided targets hold §04's base inline padding instead of the wider one those rungs normally take — 32px a side pushed the label out of a 340px column, and going below the base left the glyph of a 64px button sitting nearer the edge than the 44px one above it.

Like §18 and §21 it holds no media and no timer: it draws levels and never calls getUserMedia. The 60-second ceiling belongs to the app. This page is that app — it asks for the microphone, and falls back to a synthesised signal if you decline, so the specimen stays honest either way.

23 · Toast — §7.23

Confirms an action that has already happened and offers the one way to reverse it, without moving the content the user is looking at. That is the whole difference from §10 Message, and it is not styling: a Message is in the flow and pushes layout when it appears, which is wrong for a confirmation arriving while someone is reading something else.

Layer 1 has shipped --z-toast ranked above --z-sheet since Pass 1, with the stated reason that “a session saved confirmation must be visible over an open sheet”. This is that layer’s first consumer. Elevation 3, not 2 — it outranks a sheet, so it must not read as a lifted card sitting under one.

Live example — real fixed positioning, current theme

The component holds no timer: label going null is what removes it, so the consumer’s own undo window is the single source of truth. Trigger one and it appears bottom-centre over everything on this page — scroll while it is up; it does not move.

One at a time, and it replaces — fire the second while the first is up. No queue, no stacking, no “2 items deleted”: the undo model is undo the last thing, and two stacked toasts on a 393px screen cover the control the user was aiming at. The stated consequence: an earlier action’s offer leaves the screen while its own window is still open.

24 · Draggable List — §7.24

A list of short pieces of user content that the user rearranges, merges, corrects and removes. The list is the editing surface — no separate edit mode, no toolbar, nothing in a dialog. It introduces no new primitive: §09 Content Box, §02 Icon Button, §04 CTA Button, §23 Toast and an <ol>, arranged per L3, L4, L5, L6, L9 and L13. What makes it a component rather than a composition is the state machine — twelve states, and three pairs of them mutually exclusive in a way that is easy to get wrong by hand.

L4 is the rule to look at here. The text leads in the DOM and floats a spacer the size of the control cluster; the controls are positioned into the gap it leaves. Floating the controls themselves is one rule shorter and puts both buttons ahead of the content they act on for a screen reader, on every item. And the text must stay a plain block — a flex or grid wrapper establishes its own formatting context and steps around the spacer, which fails silently: the card just reverts to the flex-row measurements.

25 · Segmented Control — §7.25

Two to four mutually exclusive options, icon and text, all visible at once. A RadioGroup underneath, not Tabs: the choice is an answer the surrounding form carries, not navigation between panels, so role="tablist" would promise a tab/panel relationship that does not exist — and take the value out of the form. Roving arrow keys and the single tab stop come from RadioGroup either way, so the keyboard behaviour is identical and only the semantics differ. Past four options a German label cannot survive the segment width; that case is §06 or a Select.

The icon is required per option rather than optional, and that follows from the truncation rule: labels ellipse at one line, so the glyph is the cue that survives a clipped label for a sighted user. Screen readers are unaffected — CSS truncation never touches the accessibility tree, so the full label is still announced.
